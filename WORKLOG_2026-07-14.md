## Ghidra finding: superb's resolution selection (the big one)

Answers "what resolution does superb actually run?" from the decompile
(`tools/ghidra/output/string_xref_analysis.txt` ~41033 and ~8061):

- Sensor detect reads `SENSOR` from `/etc/conf.d/syscfg/sensor.sh`.
  For `sc635hai`: VI = 3200x1800, MAX_FRAME_RATE = 15, capability class
  `0x5061` -- upgraded to `0x5081` (4K class, same as imx678) when the
  OEM model field `hwinfo._604_4_ == 0x51`.
- The `StreamVideoQuality` handler maps class -> encode resolution:
  `0x5061` -> 3200x1800 native; `0x5080/0x5081` -> **3840x2160 upscaled**,
  QP min/max **35/44**, max bitrate **4096 kbps**.
- Our camera runs the `0x5081` path: the QP 35/44 extracted from superb's
  live VENC only gets set on that branch.

Conclusions:
1. Superb's "4K" is a VPSS upscale of the 3200x1800 sensor. Our
   `ipc_daemon` (VPSS ext chn 3 -> 3840x2160, 4096 kbps, QP 35-44)
   now matches superb exactly.
2. The full-screen 4K-monitor difference seen earlier was almost
   certainly the old native-1800p stream vs superb's 4K stream being
   player-scaled differently -- already addressed by commit ac01622.
3. Superb ships *native 3200x1800* encoding on lower-tier OEM models of
   this same sensor. Future quality experiment: encode native and let
   the client scale (one fewer resample generation).

Documented in DRIVER_INTERNALS.md ("Superb resolution selection").

## Code fixes applied

### driver/daemon/hal/venc.c
1. **Watchdog starvation** (real bug): `watchdog_feed()` was only called
   on select() timeout or after a video frame. If VENC stalled while
   audio kept select() waking (~every 40ms), the feed was never reached
   -> hard reboot after 120s. Feed now unconditional at loop top;
   removed the two redundant feed sites.
2. **QP block converted to read-modify-write** (was: memset + set, which
   zeroes SDK defaults for all rc_param fields not explicitly set).
   Values unchanged: QP 35/44, reencode=3, i_proportion 1..100,
   qpmap off -- still superb-matched. (This was the one structurally
   good piece of the discarded experiment, re-applied without the
   experimental values.)
3. `start_param` now memset before `ss_mpi_venc_start_chn` (was passing
   stack garbage in all fields except recv_pic_num).

### driver/daemon/hal/isp.c
4. **CSC block made honest** (real bug, benign effect): it logged
   "set: (satu=50, BT709, full range)" but never modified the struct --
   a pure get/set round-trip. PQ-bin CSC values were in effect the whole
   time (and colors are confirmed good). Now log-only, except a rescue
   to satu=50 if satu reads degenerately low (<30), which is what the
   old warning message claimed to do. **No behavior change in the normal
   case.** Note: DRIVER.md's "CSC: satu=50, ext_csc=1, ct_mode=1" state
   was always just the PQ bin values, not something we set.
5. **AE route nodes 2804 -> 2802** (= VTS 2812 - EXP_OFFSET 10 =
   max_int_time). 2804 is superb's value for its VTS=2814; on our VTS it
   exceeded the AE limit and was silently clamped. Cosmetic-to-nil
   runtime difference; docs and code now agree.

### driver/daemon/main.c
6. **SIGPIPE: crash handler -> SIG_IGN** (robustness): previously an
   RTSP client disconnecting mid-write could raise SIGPIPE, which the
   crash handler turned into daemon exit *with watchdog disarmed* ->
   camera dead until manual restart. Writes now return EPIPE instead.
7. **sig_handler re-entrancy guard**: second SIGINT/SIGTERM during
   teardown now `_exit(1)` instead of starting a nested teardown.

### driver/src/sc635hai_sensor_ctl.c
8. **Mirror/flip register encoding fixed** (latent bug -- function is
   not currently called): wrote `mode & 0x03` (0x00-0x03) to reg 0x3221,
   but the sensor encoding is 0x00/0x06/0x60/0x66 (DRIVER.md table).
   Now uses a lookup table. Comment added: caller must also fix ISP
   bayer_format when flipping (effective Bayer order changes). Relevant
   for the planned flip toggle.
9. I2C write short-write check (`ret != 3` instead of `ret < 0`).

### driver/src/sc635hai_cmos.c
10. Defensive clamp of the `again` table index in `cmos_gains_update`
    (AE lib passes an index; OOB would read past g_again_table and
    compute a bogus fine-gain register).
11. Comment fix: max dgain is ~15.875x, not ~31.875x.

## Reviewed, deliberately NOT changed

- **Analog gain range-1 overlap** (sc635hai_cmos.h): table entries
  32-63 span 2048-4032, but DRIVER.md/Rockchip document range 1
  (0x3E08=0x01) as capped at ~2720 where 0x80 (2.66x) takes over.
  `cmos_again_calc_table` linear-scans a non-monotonic table, so gains
  2723-4032 resolve inside range 1 and range 2's low entries are
  unreachable. If the hardware genuinely caps range 1, actual gain
  diverges from AE's belief in the 2.7-3.9x window. User reports gain
  behavior is great, so left alone -- needs an on-camera A/B (fix would
  make calc_table skip range-1 indices > 42). Flagged for later.
- **3DNR / BNR / sharpen tuning**: left at committed superb-matched
  values; the discarded experiments were inconclusive.
- Dead code left in place: `sc635hai_default_reg_init` (unused),
  `g_again_info[].gain_max`/`reg_fine_step` fields (never read).
- `sig_handler` still calls full teardown from signal context (not
  async-signal-safe in theory, but battle-tested on this hardware and
  the watchdog dance is timing-critical -- not worth destabilizing).
